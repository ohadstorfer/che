This is a companion to [`course-spec.md`](course-spec.md): that spec covers content, schema, runtime and the authoring pipeline. ## 0. Decisions

| Area | Decision | Why |
|---|---|---|
| Order of work | **Measure first.** Nothing that tunes difficulty or scheduling ships before the telemetry that can show whether it worked. | Duolingo's 2016 A/B tests are the lesson: HLR with per-word weights looked better offline and was worse live (HIW §2.3). |
| Scheduler | **SM-2 stays.** FSRS is evaluated offline once there is data; HLR is not a candidate. | HLR loses to "predict the average" on public data; FSRS beats both (HIW §2.5). |
| Difficulty model | **Rules now, measured.** A per-learner offset nudges the ladder from recent accuracy. A learned difficulty model (Elo) waits for enough learners. | Birdbrain needs volume; one learner's history can't estimate difficulty per exercise (HIW §3). |
| Target accuracy | **First-try accuracy 85–92%** per round. | Duolingo keeps average session accuracy ~93% on purpose (HIW §1.4). |
| Unit gate | The unit's **review lesson is a mastery check** (≥ 80% first try). The path waits for it, but never more than 3 attempts. | Duolingo 2026 end-of-unit mastery session (HIW §1.3), minus the frustration. |
| Lesson density | **4–6 new forms per lesson.** | Duolingo 5–7 (HIW §1.4). Che's authored lessons are at 2–3. |
| Grading | Accents and ñ are **taught, not ignored**: a missing accent is accepted with a note; a missing ñ is a typo. | Today `norm` folds both, so "ano" is accepted for "año" (`src/lib/answers.ts:29`). |
| Accepted answers | Grow from **learner reports**, resolved by a reviewer into `es_alt`. | Duolingo: about 10% of reports are valid, and they are the main source of new answers (HIW §6). |
| LLM at runtime | **Explain my answer** only, on tap, cached, voseo-checked. Nothing else calls a model while a learner is in a lesson. | Cost and control. |
| Not doing | XP, leagues, gems, hearts/energy, decaying strength meters, typed free-text sentence translation, speech grading, a notification bandit, HLR. | See §14. |

## 1. Telemetry — `rounds`, richer `review_logs`, `srs_commits`

Every later workstream reads these tables.

### 1.1 Schema

```sql
-- One row per played round: a lesson, a practice round, a story, a placement test.
create table public.rounds (
  id              uuid primary key,                    -- generated by the client, so logs can reference it before the insert lands
  user_id         uuid not null references auth.users on delete cascade,
  kind            text not null check (kind in ('lesson','practice','free','mistakes','story','placement','unit_check')),
  lesson_id       uuid references public.lessons,
  local_date      date not null,
  started_at      timestamptz not null default now(),
  finished_at     timestamptz,                         -- null = abandoned
  planned_items   smallint not null,                   -- queue length at start, intros and tips excluded
  answered        smallint not null default 0,         -- graded first attempts
  first_try_wrong smallint not null default 0,
  retries         smallint not null default 0,
  score           smallint check (score between 0 and 100),
  ladder_offset   smallint not null default 0,         -- §4.2, the value the round was built with
  promoted        smallint not null default 0,         -- §4.1, items the adaptive tail made harder
  app_version     text
);
create index rounds_user_idx on public.rounds (user_id, started_at desc);

alter table public.review_logs
  add column round_id    uuid references public.rounds on delete cascade,
  add column item_index  smallint,                     -- position in the queue
  add column sentence_id uuid references public.sentences,
  add column direction   text check (direction in ('es_to_en','en_to_es')),
  add column correct     boolean,                      -- the truth; `rating` stays for old readers
  add column is_retry    boolean not null default false,
  add column promoted    boolean not null default false,
  add column hinted      boolean not null default false,  -- §6.4
  add column note        text check (note in ('accent','typo','enye')),  -- §6.1
  add column latency_ms  integer,                      -- exercise shown → check pressed
  add column answer      text;                         -- what she built/typed, only when wrong or noted
create index review_logs_round_idx on public.review_logs (round_id);
create index review_logs_sentence_idx on public.review_logs (sentence_id) where sentence_id is not null;

-- What the scheduler did, once per form per round. Enough to replay any scheduler offline.
create table public.srs_commits (
  id             bigint generated always as identity primary key,
  user_id        uuid not null references auth.users on delete cascade,
  form_id        uuid not null references public.forms on delete cascade,
  round_id       uuid references public.rounds on delete set null,
  seen           smallint not null,                    -- exercises that drilled the form this round
  wrong          smallint not null,
  rating         smallint not null check (rating between 0 and 3),
  scheduled      boolean not null,                     -- false = filler; state unchanged unless it lapsed
  elapsed_days   real,                                 -- since the previous commit; null on first
  prev_interval  real, prev_ease real, prev_due_at timestamptz, prev_state text,
  next_interval  real, next_ease real, next_due_at timestamptz, next_state text,
  created_at     timestamptz not null default now()
);
create index srs_commits_user_form_idx on public.srs_commits (user_id, form_id, created_at);
```

**RLS:** the owner can insert and read `rounds` and `srs_commits`, as for `review_logs`. Staff read everything through the §10 views, which are `security definer` and never return `user_id`.

**`finish_lesson`** gains `p_round_id uuid default null`. When it is given, the function sets `finished_at`, `score`, `answered`, `first_try_wrong` and `retries` from its arguments in the same transaction. The client passes the tallies it already keeps (`firstTries`, `retries` in `src/app/practice.tsx`).

### 1.2 Client

- **`practice.tsx` load effect:**
  - `roundId = crypto.randomUUID()`.
  - Insert the `rounds` row fire-and-forget with `kind`, derived from the route: `lessonId` → `lesson` or `unit_check` (§3); `buildSession` → `practice`; the free fallback → `free`; `?mode=mistakes` → `mistakes`.
- **`onAnswered`:** every `review_logs` insert carries `round_id`, `item_index`, `sentence_id`, `direction`, `correct`, `is_retry`, `promoted`, `hinted`, `note` and `latency_ms`. `answer` is filled only when wrong or noted.
  - `latency_ms` comes from a `shownAt` ref reset when `index` changes.
  - Exercise components report the raw answer through `onAnswer(correct, extra?: { answer?: string; note?: Note })`.
- **`commitIfDone`:**
  - Inserts an `srs_commits` row every time it decides, including when it returns early for right filler (`scheduled=false`, `prev_* = next_*`).
  - `elapsed_days` = now − the form's previous `updated_at`, which `liveStates` already holds.
- **`src/lib/demo.ts`:** the stand-in client stores `rounds` and `srs_commits` like any table, and its `finish_lesson` accepts `p_round_id`.

### 1.3 Tests

- `supabase/tests/course_schema.test.mjs`:
  - RLS on the new tables (owner only).
  - `finish_lesson` with `p_round_id` stamps the round.
  - A round of another user can't be stamped.
- `scripts/engine/test/replay.test.mjs`: grouping `review_logs` by `(round_id, form_id)` reproduces `srs_commits.seen/wrong` for a fixture round.

**Done when:** one played lesson on fixtures leaves one `rounds` row, one `review_logs` row per exercise with `round_id`, and one `srs_commits` row per graded form. The numbers must agree with each other.

## 2. Measurement — accuracy reports and the tuning loop

### 2.1 Views (staff only, no user ids)

```sql
create view public.engine_round_stats with (security_invoker = false) as
select date_trunc('week', started_at) as week, kind,
       count(*) filter (where finished_at is not null) as finished,
       count(*) filter (where finished_at is null)     as abandoned,
       avg(score) filter (where finished_at is not null) as avg_score,
       percentile_cont(0.5) within group (order by score) as median_score
from public.rounds group by 1, 2;

create view public.engine_mode_stats with (security_invoker = false) as
select date_trunc('week', reviewed_at) as week, mode, promoted,
       count(*) filter (where not is_retry) as first_tries,
       avg((not correct)::int) filter (where not is_retry) as fail_rate,
       percentile_cont(0.5) within group (order by latency_ms) as median_ms
from public.review_logs where correct is not null group by 1, 2, 3;
```

Both are wrapped in `staff_*` functions that check `is_staff()`. The dashboard (course-spec §5) gets an **Engine** page with these two tables plus the §10 views.

### 2.2 Script

`scripts/engine/report.mjs` prints the same numbers for a date range from the linked project. It uses `npx supabase@2 --linked`, per the memory note on CLI login. It also prints:

- first-try accuracy by rung (`sentence_meaning` / `sentence_gap` / `sentence_build|listen`) and by word angle (recognition / production);
- the share of rounds outside the 85–92% band;
- abandonment by item index, i.e. where people quit.

### 2.3 Tuning table

When a measured number is out of band for at least 2 consecutive weeks, with at least 50 rounds, move **one** constant, then wait two weeks.

| Symptom | Constant | Direction |
|---|---|---|
| Rounds > 92% | `RUNG_BUILD_AT` (`src/lib/sentences.ts`) | 2 → 1 |
| Rounds > 92%, words mostly recognition | `SETTLED_DAYS` (`src/lib/session.ts:44`) | 7 → 5 |
| Rounds < 85%, sentence builds failing > 25% | `GLUE_UNLOCK_PASSES` | 5 → 7 |
| Rounds < 85%, typing failing > 30% | `SETTLED_DAYS` | 7 → 10 |
| Practice rounds abandoned past item 12 | `MAX_SESSION_ITEMS` | 18 → 15 |
| Unit check first-attempt pass < 60% | lesson density (§5) or the unit's sentences (§10) | content, not constants |

**Done when:** the report runs against the live project and the Engine page renders on fixtures.

## 3. Unit mastery check

### 3.1 Behaviour

- The last lesson of a unit (`kind = 'review'`, already generated by `scripts/course/lib/outline.mjs:113`) plays as a **unit check**.
- The path advances past it only when it is **passed**: first-try score ≥ `UNIT_PASS_SCORE = 80`.
- **Fail:**
  - The finish screen shows the words she missed (from the round's wrong `review_logs`) and one button: **Try again**.
  - The lesson stays current.
  - A failed attempt still credits the day (`finish_lesson` runs as usual).
- **Attempts:**
  - The 3rd attempt passes on completion whatever the score, recorded `passed_by = 'attempts'`.
  - The check is a checkpoint of understanding, not a wall. Duolingo's version "won't let users proceed" (HIW §1.3); Che softens that deliberately.
- **Section checkpoint:** every lesson of a section's last unit (`kind = 'checkpoint'`) behaves the same way, scoped to the whole section.

### 3.2 Content — the `recap` slot

```sql
alter table public.lesson_slots drop constraint lesson_slots_kind_check;
alter table public.lesson_slots add constraint lesson_slots_kind_check
  check (kind in ('teach','drill','match','tip','review','recap'));
alter table public.lesson_slots add column scope text check (scope in ('unit','section'));
```

A `recap` slot resolves to `review_count` screens over forms of its scope that she has a state for:

1. **Selection:**
   - Order by weakest first: `lapses desc`, then `ease_factor asc`, then `interval_days asc`.
   - Each form appears at most once.
   - At least half the screens are production: `sentence_build`, `sentence_listen`, `word_build`, or `typing` when settled.
2. **Carriers:** sentences from the scope are chosen with `pickReviewSentences` (with `pad: false`) and the rung the ladder gives, but **never below `gap`**. A check doesn't ask for meaning only.
3. **Scheduling:**
   - Forms that are due are scheduled normally.
   - Forms that are not due are filler, but a miss still lapses them (existing rule).

Authoring (`scripts/course/fixtures/*.yaml`): `{recap: 8}` and `{recap: 12, scope: section}`. A unit check is typically `tip?` + `recap: 8` + 2–3 pinned `drill`s of the unit's hardest sentences at `sentence_build`.

### 3.3 Schema and path

```sql
alter table public.lesson_progress
  add column attempts   smallint not null default 1,
  add column passed     boolean  not null default true,
  add column passed_by  text check (passed_by in ('score','attempts','placement'));
```

`finish_lesson(p_local_date, p_lesson_id, p_score, p_round_id)` changes:

- It looks up `lessons.kind`.
- For `review` / `checkpoint`: `passed = coalesce(existing.passed, false) or p_score >= 80 or attempts >= 3`, and `attempts += 1` on conflict.
- For other kinds: `passed = true`.
- It returns `passed` as an extra output column.

`src/lib/course.ts`:

- `loadProgress` selects `lesson_id, passed` and returns only passed ids.
- `currentIndex` is unchanged, since it already walks to the first lesson not in the set.

`home.tsx`: the current coin of a failed check shows its attempt count ("2/3").

### 3.4 Tests

- `db:test`: the pass, fail, and 3rd-attempt paths; the best score kept; `passed` never goes back to false.
- `scripts/engine/test/recap.test.mjs`: at most one screen per form, the production share, no meaning rung.

**Done when:** on fixtures, failing unit 2's check keeps it current, the third attempt moves the path on, and a pass on the first attempt moves it on.

## 4. Adaptive difficulty

### 4.1 Adaptive tail, inside a round

When the first `TAIL_AFTER = 6` graded, first-attempt items of a round are **all correct**, the unanswered items after the current one are **promoted one step** before they are shown. Duolingo does the same (HIW §3.4).

| From | To | Condition |
|---|---|---|
| `sentence_meaning` | `sentence_gap` | never for `sentence_intro` |
| `sentence_gap` | `sentence_build` | the sentence has no locked glue |
| `sentence_build` | `sentence_listen` | `audio_path` present |
| `multiple_choice` / `true_false` / `listen` | `word_build` | — |
| `word_build` | `typing` | single word, state exists |

Rules:

- **Excluded:** intros, tips, matching blocks, retries, and items already at the top step.
- **Once per round:** promotion is triggered at most once.
- **Label:** promoted items show the **Harder** label (§6.5).
- **Scoring:**
  - A miss on a promoted item counts as **at most one wrong** toward the form's rating (→ `difícil`, never a reset from promotion alone).
  - It is re-asked as usual.
  - It counts in the lesson score. Being challenged shouldn't cost a streak of good days, but the score should stay honest.
- **Code:** a pure function `promoteTail(queue: QueueItem[], from: number, ctx): QueueItem[]` in `src/lib/session.ts`, called from `onAnswered`. It sets `promoted: true` on changed items and `rounds.promoted`.

### 4.2 Ladder offset, across rounds

The client computes `ladderOffset ∈ {−1, 0, +1}` at round build from the learner's last `OFFSET_WINDOW = 5` finished rounds (`rounds.score`):

```
mean ≥ 95  → +1
mean ≤ 75  → −1
otherwise  →  0      (fewer than 3 finished rounds → 0)
```

Effects are applied through one `Ladder` object passed into the builders, replacing today's module constants at the call sites:

| Knob | −1 | 0 | +1 |
|---|---|---|---|
| `RUNG_GAP_AT` | 1 | 1 | 0 |
| `RUNG_BUILD_AT` | 3 | 2 | 1 |
| `SETTLED_DAYS` | 10 | 7 | 5 |
| `sentenceCap` | −1 | — | +1 |
| `TAIL_AFTER` | never | 6 | 4 |

- **Existing rule kept:** the "fails yesterday" rule in `sentenceCap` stays and stacks.
- **Recording:** `rounds.ladder_offset` records the value used, so §2 can check that the offset actually moves accuracy back into the 85–92% band.
- **Refactor:**
  - `sentences.ts` and `session.ts` export `DEFAULT_LADDER`.
  - `rungFor`, `sentenceCap`, `exercisesFor`, `buildSession` and `resolveSlots` take `ladder` as a parameter, defaulting to `DEFAULT_LADDER`, so existing tests hold.

### 4.3 Learned difficulty (Elo) — gated on data

**Gate:** not built until **≥ 30 learners with ≥ 10 finished rounds each**. Until then it runs offline only.

Model (Birdbrain V1 as described, HIW §3.2):

```
components of an exercise: mode, rung, each content form in it (sentence) or the form (word)
P(correct) = σ(θ_user − Σ_k d_k)
after each first-try answer y ∈ {0,1}:  e = y − P
θ_user += η_u · e          η_u = 0.1
d_k    −= η_d · e / n      η_d = 0.05, n = number of components
init θ = 0, d = 0; learners start at the mean.
```

- **Offline phase:** `scripts/engine/fit-elo.mjs` replays `review_logs` in time order and reports calibration: predicted vs actual accuracy in 10 bins, and log loss against a per-mode constant.
- **Online phase:** only if calibration beats the constant by ≥ 0.02 log loss.
  - Tables `difficulty_params(component text pk, d real, n int)` (nightly job) and `profiles.ability real`.
  - The session builders pick, among the candidate angles for a form, the one whose predicted P is closest to **0.88**.
  - The Ladder (§4.2) then becomes a fallback for cold starts.

## 5. Lesson density and ramp

### 5.1 Authoring rules

The lesson count per unit becomes derived instead of `DEFAULT_LESSONS = 5` (`scripts/course/lib/outline.mjs:35`):

```
teaching lessons = max(2, ceil(new drillable forms / 5))
unit = teaching lessons + (story, §8, when the unit has one) + 1 review lesson (the unit check, §3)
```

A `lessons: n` override in the YAML still wins.

### 5.2 Linters (added to `scripts/course/lib/content.mjs`, run by `course:demo` / `course:seed`)

| Rule | Checks | Severity |
|---|---|---|
| `lesson.density` | a `lesson`-kind lesson has 4–6 `teach` slots (3 allowed in a unit's first lesson) | flag |
| `lesson.length` | resolved canonical screens 12–20 | flag |
| `lesson.ramp` | a form's first drill after its `teach` is not pinned above `sentence_gap`, unless an earlier lesson taught it | flag |
| `lesson.production` | every teaching lesson has ≥ 1 `sentence_build` / `sentence_listen` drill | flag |
| `unit.check` | the review lesson has a `recap` slot with `review_count ≥ 6` | fail |
| `unit.coverage` | every drillable form the unit introduces is drilled ≥ 3 times across its lessons (teach + drills + match) | flag |

### 5.3 Re-authoring

- 3 teaching lessons of 4–5 new forms each
- 1 unit check

`npm run course:demo` and a new seed migration follow.

**Done when:** `course:demo` passes with no density flags on units 1–2, and a played lesson is 12–20 screens.

## 6. Grading

### 6.1 Accents and ñ

`src/lib/answers.ts`:

```ts
/** Case- and punctuation-insensitive, accent-SENSITIVE, ñ kept. */
export const normStrict = (s: string) =>
  s.toLowerCase().normalize('NFC').replace(/[^\p{L}\p{N}]/gu, '');
/** Folds accents but keeps ñ as its own letter. */
export const norm = (s: string) =>
  s.toLowerCase().replace(/ñ/g, ' ').normalize('NFD').replace(/\p{Diacritic}/gu, '')
   .replace(/ /g, 'ñ').replace(/[^\p{L}\p{N}]/gu, '');

export type Note = 'accent' | 'typo' | 'enye';
export interface Graded { correct: boolean; note?: Note; expected: string }

export function typedAnswerMatches(input: string, form: Form, allForms: Form[]): Graded
```

Order of checks:

1. `normStrict(input)` matches an accepted form → correct, no note.
2. `norm` matches → correct, `note: 'accent'`.
3. Only difference is ñ ↔ n:
   - If the n-spelling is itself a course word, it is wrong.
   - Otherwise correct with `note: 'enye'` when the word has ≥ 5 letters; wrong below that ("ano" is not "año").
4. The existing one-edit rule (≥ 5 letters, not itself a course word) → correct, `note: 'typo'`.
5. Otherwise wrong.

Everything else:

- **Other comparisons:** `builtAnswerMatches`, `sentenceAnswerMatches` and `missedForms` use the new `norm`, which keeps ñ. Tiles are exact anyway.
- **Verdict UI** (`src/components/exercise-frame.tsx`): a correct answer with a note gets an amber sub-line. **Accent:** "Watch the accent: *tenés*". **ñ:** "It's *ñ*: *compañero*". **Typo:** "Typo — *medialuna*".
- **Grading:** a noted answer is correct for SM-2 and the score. `note` is logged (§1).
- **Synonym (as built, 2026-09-18):** a fourth note. The prompt shows one meaning of the word (course-spec §1.3, `tokens[].gloss`); a course word that also means it (`bien` typed for "well" when `bueno` was asked) is correct with `note: 'synonym'` — "That works too. This one was *bueno*". Migration `20260918000003_synonym_note.sql` widens the `review_logs.note` check.
- **Tests** in `scripts/course/test/answers.test.mjs`:
  - año/ano rejected
  - compañero/companero noted
  - tenes → accent
  - sos/soy still wrong
  - existing cases unchanged

### 6.2 Report "my answer should be accepted"

```sql
create table public.answer_reports (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references auth.users on delete cascade,
  round_id     uuid references public.rounds on delete set null,
  sentence_id  uuid references public.sentences,
  form_id      uuid references public.forms,
  mode         text not null,
  answer       text not null,                 -- as submitted
  answer_key   text not null,                 -- answerWords(answer).join(' ')
  status       text not null default 'open' check (status in ('open','accepted','rejected','duplicate')),
  resolved_by  uuid references auth.users,
  resolved_at  timestamptz,
  note         text,
  created_at   timestamptz not null default now(),
  check (sentence_id is not null or form_id is not null),
  unique (user_id, sentence_id, form_id, answer_key)
);
```

- **RLS:** owner insert/read, staff read/update.
- **Client:** a wrong verdict on `sentence_build`, `sentence_listen`, `typing` or `word_build` shows a small flag button, "My answer should be accepted". One tap inserts the report and changes the button to "Reported". The verdict is not re-graded.
- **Dashboard queue** (`/admin/reports`, course-spec §5):
  - Open reports are grouped by `(sentence_id|form_id, answer_key)` with a count, sorted by count then age.
  - Each group shows the sentence, `es` + `es_alt`, the report, and whether the answer passes `es_alt.legal` (the same linter, run in the browser).
  - **Accept:** append to `sentences.es_alt` (or a new `forms` alternative, §6.2.1) through the revision helper, and resolve every report in the group as `accepted`.
  - **Reject:** resolve as `rejected` with an optional note.
- **Ranking later:** once there are ≥ 500 resolved reports, add Duolingo's logistic-regression ranking (HIW §6). Not before.

#### 6.2.1 Word-level alternatives
`forms` gains `alt text[] not null default '{}'`: other spellings accepted when typing the form (e.g. a lexicalised variant). `sameAnswer` includes them.

### 6.3 Explain my answer

- **Trigger:**
  - A wrong verdict on a sentence exercise or on typing shows **Why?** next to the correct answer.
  - One tap calls the edge function.
  - The result renders in the verdict panel. It never blocks Continue.
- **Edge function** `supabase/functions/explain-answer`:
  - **Input:** `{ sentence_id | form_id, mode, answer }`; the function loads everything else server-side.
  - **Cache key:** `sha256(sentence_id|form_id, mode, answer_key)`.
  - **Table:** `explanations(key text pk, body_md text, model text, created_at, flagged boolean default false)`. The service role writes; authenticated users can read unflagged rows.
  - **Rate limit:** 30 generated (non-cached) explanations per user per day, counted in `notification_events`-style rows or a small `explain_usage` table.
- **Prompt inputs:**
  - `es`, `en`, every accepted answer, the learner's answer, and `missedForms(...)` with each form's lemma, gloss and `features`
  - the unit's `grammar_focus` and tip bodies
  - Appendix B of course-spec (the rioplatense style spec)
- **Instructions to the model:**
  - English, ≤ 60 words.
  - Explain the one difference that matters.
  - Use vos forms only, and never mention tú.
  - No praise.
- **Model:** `claude-sonnet-5`, `max_tokens` 200, temperature 0.
- **Output guard:**
  - Run the `voseo.no_tuteo` and `lexicon.regional` denylists (`scripts/course/lib/rules.mjs`, ported to the function) over every Spanish word in the output.
  - On a hit, discard the output and return a generic line built from the diff: "The answer is *X*. You wrote *Y*."
- **Review:** staff see explanations in the dashboard, most-served first, and can flag or edit them.

### 6.4 Hints on old sentences

- **Where:**
  - In `review` items (from a lesson's review slot), practice rounds and recaps.
  - A token is tappable (dotted underline, peek panel as in `SentenceIntro`) when its form is drillable **and** either:
    - `interval_days < SETTLED_DAYS`, or
    - the form's unit is ≥ 3 units behind the learner's current unit.
  - Glue tokens are never tappable.
- **Scoring:**
  - A tap marks that form `hinted` for this exercise and logs it.
  - That form's rating for the round is capped at **`difícil` (1)**.
  - The exercise's correctness is unchanged.
- **No hints:** gap blanks and builds, which would reveal the answer.

### 6.5 "Harder" label

A small chip above the prompt on:

- `sentence_build` and `sentence_listen` when the sentence's rung was reached this week,
- `typing`,
- any promoted item (§4.1).

Copy: "Harder". No other effect. Duolingo found labelling raises effort (HIW §3.4).

## 7. Placement and jump-ahead

### 7.1 Entry points

- **Onboarding:** "New to Spanish" (path from the start) or "I know some Spanish" (placement over sections 1–3).
- **Path, per section:** each section header after the current one gets **Jump here**, a test over every unit between the current position and that section's start.
- **Path, per unit:** each unit banner after the current unit gets **Jump here** too, a test over every unit from the current one up to (not including) that unit. Tapping a locked banner opens the guidebook sheet (§9) with the button at its foot; a banner more than one section ahead shows the section's button instead, so a single test never spans more than one section's worth of units.

### 7.2 The test

- **Build:** `buildPlacement(userId, fromOrder, toOrder)` in `src/lib/placement.ts`, pure given its data.
- **Walk:** units in course order, **2 items per unit**:
  - One sentence from the unit at `sentence_build` (no glue lock check; glue from the span counts as known).
  - One of: a `typing` item for the unit's most frequent verb form, or a `sentence_gap`.
- **Stop:**
  - As soon as **2 units in a row** each have ≥ 1 miss, or a unit has 2 misses.
  - The **placement boundary** is the first unit with ≥ 1 miss.
- **Cap:** 30 items. No re-asks, no hearts, no intros, no tips. `rounds.kind = 'placement'`.
- **Jump here** (section or unit): the span is `[current unit, target unit)`.
  - A span of **1 unit** asks **4 items** from it (2 builds, 1 typing, 1 gap) and passes with at most one miss.
  - A span of 2+ units asks 2 items per unit and passes if every unit has 0 misses, allowing one miss overall.
  - Pass: the path moves to the target unit's first lesson. Fail: the path stays put and the finish screen names the first unit that tripped.
  - No stop rule: a jump test runs to the end of its span, capped at 30 items (the unit-banner button is hidden when the span would need more).
- **Tie-in:** the unit check (§3) is not required for units skipped by placement.

### 7.3 Effects — `apply_placement` RPC (security definer)

```sql
create function public.apply_placement(
  p_round_id uuid, p_through_order smallint,
  p_passed_form_ids uuid[], p_failed_form_ids uuid[]
) returns void ...
```

- **Progress:** `lesson_progress` rows for every published lesson in units with `course_order < p_through_order`, `passed_by = 'placement'`, `score` null. Existing rows are untouched.
- **Form states:** for every drillable form of those units with no state, insert:

  | Form | State | Interval | Due |
  |---|---|---|---|
  | In `p_passed_form_ids` | `review` | 7 | now + 3–10 days, spread by `hashtext(form_id)` |
  | In `p_failed_form_ids` | `learning` | 0 | now |
  | Any other | `review` | 3 | now + 1–7 days, spread the same way |

  Every inserted row gets `repetitions = 1` and `ease = 2.5`.

  So review slots and practice verify the skipped material over the next week instead of all at once.
- **Placement boundary:** `profiles.placed_through smallint default 0` is set to `greatest(placed_through, p_through_order − 1)`.
- **Streak:** the client calls `finish_lesson(p_local_date, null, score, p_round_id)`, so the test credits the day.

### 7.4 The ladder after placement

Skipped learners have no sentence history, which would hold everything at the meaning rung and lock all glue. In `src/lib/sentences.ts`:

- **Glue:** `hasLockedGlue` treats a glue form as unlocked when `form.unit_order ≤ placed_through`.
- **Rung:** `rungFor` returns at least `gap` for sentences whose unit is ≤ `placed_through`.
- **Cap:** `sentenceCap` starts at `INTRO_IN_SENTENCE_MIN_CAP` (4) instead of 2 when `placed_through > 0`.

**Demo:** the stand-in client implements `apply_placement` on its tables.

**Tests:**
- The boundary logic, including the stop rule, over scripted answer sequences.
- The RPC: no overwrite of existing states; due dates spread.

**Done when:** on fixtures, a new learner answering everything right through unit 2 lands on unit 3 with unit 1–2 words due across the week; and a learner on unit 1 who taps unit 2's banner, passes its 2-per-unit test over unit 1, lands on unit 2's first lesson.

## 8. Stories

### 8.1 Model

A story is a lesson of `kind = 'story'` (already allowed by `20260916000001_sections_and_lesson_kinds.sql`) whose content is ordered lines:

```sql
create table public.story_lines (
  id           uuid primary key default gen_random_uuid(),
  lesson_id    uuid not null references public.lessons on delete cascade,
  ordinal      smallint not null,
  speaker      text not null,                         -- a character name, or 'narrator'
  sentence_id  uuid not null references public.sentences,
  question     jsonb,                                 -- null, or one of the shapes below
  unique (lesson_id, ordinal)
);
-- question shapes:
--   {"type":"meaning"}                                     pick the line's meaning (meaningOptions)
--   {"type":"gap","form":"<form_id>"}                      fill a word of the line (gapOptions)
--   {"type":"build"}                                       rebuild the line from tiles
--   {"type":"choice","prompt_en":"…","options_en":["…","…","…"],"correct":1}
--                                                          comprehension about the story so far
```

- **Line sentences:** these are ordinary `sentences` rows with `kind = 'dialogue'`, so tokens, linters, `es_alt` and audio all apply unchanged.
- **RLS:** same as `lesson_slots`.

### 8.2 Constraints (linter `story.shape`, fail unless noted)

- 8–16 lines, 2–3 speakers (names are `propn` forms), ≥ 4 questions, and never two questions back to back.
- Every form is available by the story's unit, as for any sentence.
- **Known language:** ≥ 90% of content tokens come from forms taught **before this unit** or in lessons of this unit that precede the story. At most 10% new, and those new forms must be taught in the same unit.
- At least one `choice` question that can't be answered from the last line alone. This is a flag: judged by the AI reviewer, not by machine.

### 8.3 Playing

- **Route:** `src/app/story.tsx` (`/story?lessonId=`).
- **Lines:**
  - Lines appear one at a time as chat bubbles, left/right by speaker, with audio when present.
  - Tapping Continue reveals the next line.
  - Every content token is tappable for its gloss (§6.4 rules do not cap anything here: stories are for reading).
- **Questions:**
  - A question renders under its line with the same exercise component the practice screen uses.
  - Answers go through the same `onAnswered` path: `review_logs`, SM-2 for due forms only, everything else filler.
  - No re-asks, and no unit-check rules.
- **Finish:** `finish_lesson` with `kind = 'story'` credits the day and moves the path.
- **Prerequisite refactor:** move the exercise components out of `src/app/practice.tsx` (`MultipleChoice`, `Choices`, `SentenceLine`, `SentenceGap`, `SentenceBuild`, `TileBuilder`, `PlayButton`, …) into `src/components/exercises/`, next to the existing `exercise-frame.tsx`. Keep the scoring state machine in a hook `useRoundScoring` (`src/lib/round.ts`), so `practice.tsx` and `story.tsx` share it. No behaviour change; verified by playing a fixture lesson before and after.

### 8.4 Authoring

```yaml
hola-che:
  stories:
    en-la-parada:            # becomes a lesson of kind story, placed before the unit check
      title: "At the bus stop"
      lines:
        - {speaker: Sofi, es: "Hola, che. ¿Todo bien?", en: "Hi. All good?"}
        - {speaker: Martín, es: "Todo bien, ¿y vos?", en: "All good, and you?", question: {type: meaning}}
        - …
```

`buildContent` creates the dialogue sentences, the lesson, and `story_lines`.

**Placement on the path:** one story per unit from unit 3 on, placed immediately before the unit check.

**Done when:** one story in unit 2 of the fixtures plays end to end, logs its answers, and advances the path.

## 10. Content quality loop

### 10.1 Views (staff, security definer, no user ids)

```sql
-- Per sentence, last 60 days, over all learners.
create view public.sentence_quality as
select s.id, s.unit_id, s.es,
       count(*) filter (where not l.is_retry)                               as tries,
       avg((not l.correct)::int) filter (where not l.is_retry)              as fail_rate,
       avg((not l.correct)::int) filter (where not l.is_retry and l.mode in ('sentence_build','sentence_listen')) as build_fail_rate,
       percentile_cont(0.5) within group (order by l.latency_ms)            as median_ms,
       (select count(*) from answer_reports r where r.sentence_id = s.id and r.status = 'open') as open_reports
from public.sentences s
join public.review_logs l on l.sentence_id = s.id and l.reviewed_at > now() - interval '60 days'
group by s.id;

-- Forms that keep lapsing, across learners.
create view public.form_leeches as
select form_id, count(distinct user_id) as learners, avg(lapses) as avg_lapses
from public.form_states where lapses >= 3 group by form_id;

-- Unit checks: first-attempt pass rate per unit.
create view public.unit_check_rates as …   -- from lesson_progress (attempts, passed_by) joined to lessons/units
```

### 10.2 Dashboard

An **Attention** list on `/admin` shows:

- sentences with `tries ≥ 20` and `fail_rate` > 0.35 at their typical rung,
- forms in `form_leeches` with ≥ 3 learners,
- units with first-attempt check pass rate < 60%,
- sentences with open reports.

Each links to the editor.

A rewrite of a flagged sentence resets nothing for learners. The sentence id stays, and `sentence_states` stays valid.

## 11. Scheduler work

### 11.1 Starting ease by morphology (flagged experiment)

- **Rule:** `srs.initialEase(form)` returns **2.3** for a form whose `features` include `verb_form: 'ger'`, `mood: 'imp'`, or `irregular: true`. Every other form gets **2.5**.
- **Data:** `FormFeatures` gains `irregular?: boolean`, authored in the outline YAML as `f: … irregular`.
- **Where applied:** `createState` in `practice.tsx`.
- **Evidence:** HLR found gerunds, participles and irregulars decay faster (HIW §2.3).
- **Why it's gated:** the prior is a guess until §11.2 can check it. It ships behind `EXPO_PUBLIC_EASE_PRIOR=1`, off by default.

### 11.2 Offline scheduler evaluation

`scripts/engine/eval-scheduler.mjs`:

1. **Traces:** export `srs_commits` in order per (user, form). A commit with `elapsed_days` and `wrong` is one observation. Recall = `wrong = 0`, the round-level proportion as in HLR (HIW §2.1).
2. **Predictions** of recall probability at `elapsed_days`, from:
   - **SM-2 proxy:** `p = 0.9 ^ (elapsed / prev_interval)`. SM-2 has no retrievability; this assumes 90% at the due date.
   - **FSRS-6** with default parameters (`ts-fsrs`), replaying the same history.
   - **FSRS-6 fitted:** parameters optimised on 80% of learners, evaluated on the other 20%.
   - **Constant:** the mean recall.
3. **Reported:** log loss, AUC, and a calibration table in 10 bins, overall and per `pos` / `features`.

**Switch criterion:** ≥ 5,000 commits from ≥ 30 learners **and** fitted FSRS log loss better than the SM-2 proxy by ≥ 0.02 on held-out learners.

**If met, migration:**
- `form_states` gains `stability real`, `difficulty real`.
- A one-off script initialises them by replaying each form's commits.
- `srs.ts` gains `scheduleFsrs` behind a flag, with target retention **0.9**.
- SM-2 columns stay populated for a release, so rollback is a flag flip.

### 11.3 Mistakes practice

- **Entry:** Practice button long-press, or a second button in the Practice sheet: **Mistakes (n)**, where n = distinct forms with a commit rating ≤ 1 in the last 14 days whose latest commit is not rating ≥ 2.
- **Round:** `kind = 'mistakes'`, up to 10 of those forms, most recent miss first. Each gets one production angle, through a sentence where one carries it (`pickReviewSentences`, ladder rung, at least `gap`).
- **Scheduling:** due forms are scheduled; the rest are filler with the lapse rule.
- **Clears:** a form leaves the list when its latest commit is ≥ 2.

## 13. Content pipeline amendments (course-spec §4, Phase 3)

These change `generate-unit.mjs` and `ai-review.mjs` before they are built.

1. **Grounding:** the generator prompt includes up to 30 **approved** sentences as style examples: 10 from the unit if any, the rest from the 3 previous units, stratified by `kind`. (DuoRadio: grounding in the curriculum's own sentences is what made generation work, HIW §7.)
2. **Over-generation:** ask for **3×** the quota per slot (intro, drills, dialogues). Keep the best by judge score (below), then by length band. Discarded candidates are stored with `status = 'retired'` and `content_reviews.notes.reason = 'not selected'` for prompt tuning.
3. **Judge rubric:** the AI reviewer scores 1–5 on **naturalness (porteño)**, **grammaticality**, **coherence**, **logic**, plus the three existing yes/no questions (course-spec §4). Scores are stored in `content_reviews.notes.scores`. Candidates with any score < 4 are not selected. The judge still never approves.
4. **Frequency linter `lexicon.frequency`** (flag):
   - Each lemma's rank comes from a Spanish subtitle frequency list, with forms summed per lemma.
   - Ceiling: rank ≤ 3,000 in section 1, ≤ 5,000 in sections 2–3.
   - `scripts/course/data/rioplatense-allow.txt` exempts regional words that subtitle corpora under-count (bondi, laburo, facturas, …).
   - The list is loaded from `scripts/course/data/freq-es.tsv`, source and license recorded in its header (open item, §15).
5. **Quotas** follow §5: per unit, 4–6 new forms per teaching lesson; per new form, 1 intro + 3 drills; plus 1 story (§8) from unit 3 on.
